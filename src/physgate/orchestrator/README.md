# `physgate.orchestrator` — the deterministic loop

This package decides what runs next and whether to merge, in Python. A model is
called once per run, at decomposition, and never to schedule, dispatch, merge or
reconcile (ARCH-001). Every awkward case, from a garbled session to a merge
conflict, is answered by code or by a person.

## What it owns

| | |
|---|---|
| `dispatch.py` | One attempt in a fresh Claude Code session: the binary's version checked against the run's, the session's own directory outside the worktree, settings from the hook layer's installer run from the read-only installation, the credential through a file by auth mode, the wall clock, and afterwards only the orchestrator's own records: the stream it captured (credential redacted), the hook layer's reading records, the hook log's node-file halts and journal appends |
| `processes.py` | Stopping a session so nothing it started is left running: the process tree collected by parent pid before the stop, SIGTERM, then SIGKILL for whatever is still alive and still the same process by start time; a stop that cannot be completed kills the session's whole process group; every `ps` call is time-limited, and one that fails is never read as "nothing runs" |
| `install.py` | The copied, read-only installation the hooks run from, held to its build at every build and reuse: its package to the source with no file the source lacks, and every file of it to a manifest of paths and digests written when it was built, the manifest itself held to a digest the build recorded beside the installation, outside it (protected at every spawn, and put back if changed), and to the digest the run recorded in its own event log when it first used the installation: the `bin` scripts every hook runs through, `pyvenv.cfg`, compiled caches, and `site-packages`, where a planted `.pth` or `sitecustomize` would run inside every hook. Also the facts each run records about it and about the state directory's filesystem |
| `decompose.py` | The run's one model call (ARCH-001): one Claude Code invocation, no tools but the structured answer, one turn, so one request. The answer is untrusted input, validated here; success with no plan fails the run. Subtask ids are minted from the seed; specifications go onto the run branch, interface nodes into the store, and the store is committed. The call writes the binary's debug log, which is read for the served model catalog and the remote feature flags (either not reported off fails the call) and then removed; only that closed-vocabulary reading is kept, on the decomposition line |
| `credentials.py` | The two auth modes: `api_key` (`ANTHROPIC_API_KEY`, through an `apiKeyHelper` script) and `subscription` (`CLAUDE_CODE_OAUTH_TOKEN`, as the binary's login file in the session's scratch configuration directory). The secret is read from the orchestrator's environment, refused if absent, never recorded, removed when the session ends |
| `managed.py` | The managed-settings tier, which `--setting-sources ""` does not govern and the agent does not write: the system managed paths are recorded, never touched; after every invocation a non-empty remote-settings cache or a changed system path is drift, and drift halts the run. So are policy limits that differ from the ones the run's decomposition call received (a file appearing or disappearing included): their digest is on the decomposition line and on every session's end. Detection, not prevention: `CLAUDE_CODE_REMOTE_SETTINGS_PATH` was measured not to replace the remote fetch, so it is not used |
| `invocation.py` | The one module that names the Claude Code binary: the pinned version, the isolated argv and an environment built from nothing, with the run's effort level (`--effort`) and output-token limit (`CLAUDE_CODE_MAX_OUTPUT_TOKENS`) on every invocation rather than the defaults of a catalog the version does not pin |
| `cli.py` | `physgate decompose` (the configuration from explicit inputs, the one call, the run started) and `physgate queue list/resolve`. `physgate run` and `physgate resume` (the harness checkout held to the recorded one, the installation's check or build timed and recorded as an `install_checked` line before any spawn, the real ports wired, the gate and reviewers from the registrations, the physics gate registered by default and built only when a run is driven, routing tokens asserted zero at the end); `physgate gate-events` (one line per gate check the run recorded, for catch accounting; a pass carries how many things it evaluated, and each event whether the paired reviewer had passed the artefact, from which review line and on what basis); `physgate catches` (per gate mode and check, over one or more `--run-dir` and an optional `--since`/`--until` window: checks run, blocking failures by reviewer verdict, distinct artefacts caught and the ones a reviewer had passed, ARCH-083's headline); the run directory belongs on a local disk where one exists. Example parameters files for both auth modes are in `examples/` |
| `record.py` | A run's durable record (configuration, event log, ledger, queue), so a run can be started without the ports a loop needs. The plan's lines mark the subtask of the role the register names as owning completion. The whole opening (start line, decomposition, plan) is held to every check its lines would meet as they are written, the register's and the replay's, before the first is written, so a refused plan leaves nothing on the record and starts no run. In a run with the integration role the opening ends with the module pairs whose interface contract is tested, read from the plan (`physgate.contracts.pairs`) |
| `loop.py` | The eight stages (ARCH-030), one subtask at a time: fresh session, reading, change check, gate (at the attempt's own nodes, and at its module once the module is complete), review only if the gate result allows it, merge or templated rejection, diff. Once every planned subtask is merged or queued, one integration gate call on the whole design: a blocking failure is an approval-queue item and the run ends escalated; under `observe` it is recorded; under `off`, or for an incomplete design, the log says integration was not gated, and why. Integration's own subtask, of the role that owns completion, is neither waited for nor judged by that call: it is dispatched after it, once the result passed or was observed, or under `off` once every other subtask merged, and never after a blocking failure or an incomplete design. Every session a process spawns, a role's or a reviewer's, follows that process's own environment line. The line is recorded at the process's start unless its first step is the run's end (done or escalated), a halt or the integration call, so it can precede a first step that then spawns nothing (the escalation question, an attempt sent to the queue, a subtask's end, an infrastructure retry, or an approve's merge or check); otherwise it is recorded once, before the first session or review the process reaches, as when a decision it takes or the call it makes leads to one. Before a subtask's attempt is dispatched the role register, held with the harness across the run and its resume, is asked whether the subtask's completion mark is what it says; a mark it does not bear out, which only a line written past the writer can carry, halts the run as a duty breach before the subtask's first line. A person's approve is carried on from the record: killed between its divergence check's stage line and the check, the next process makes the check under the stage already recorded. Refuses to start in a gate mode that needs a gate when none is registered; under gate mode `off` the stage is skipped on the record, never passed. At every attempt end that did not merge it asks the escalation question once, through the run's binding, and records the answer; the queue or the next attempt follows from that line. Refuses a run whose binding is not the interface it was handed. Resume restarts an interrupted attempt at its checkpoint with a fresh session. After integration's accepted attempt it writes each completion line the record owes, and a process whose first step is one records no environment line. A contract result the record owes is a step of its own, taken before anything else: the pair is held to the clause over the canonical graph read at the journal revision the log records, and one line records it; a failed contract blocks nothing. An interface node the pair cannot be held to halts the run (`interface_mismatch`), and so does a journal that ends before the recorded revision (`foreign_journal_line`), with no result recorded; a process killed between that incident and its halt writes the halt alone. A process whose first step is a contract result records no environment line |
| `escalation.py` | The escalation decision (ARCH-131, ARCH-132): one interface, `decide(question, state)`, timed, and the routing rule it applies whatever the backend: the third rejection, a blocked review and a review with no verdict are forced to the approval queue, a yes or a confidence below 0.8 sends any other end there. The backend register: `rules` ships (yes exactly on the forced routes, confidence 1.0); `llm` is off while the decision must spend no tokens; `tsetlin` and `laya` are parked on their experiments. Only a row that ships is bound. Imports only an allowlist: no graph, no environment, no model |
| `integration_state.py` | Integration's issued state (ARCH-051): one document built from the event log alone before integration's session is spawned (the gate mode, the system-scope result or why there is none, each planned pair's first contract result labelled first and its latest, the system requirements with the brief's own words for each one given by number), JSON-quoted on one line per value and cut at the transcript's width, so the reading check proves a whole read. Recorded by digest and length on an `integration_state_issued` line between the attempt's `resolve` and its `spawn`; replay holds the line to its place and form, the loop holds the bytes before the spawn and before the review, and a record that no longer gives them halts the run (`issued_state_mismatch`). It is state, not a message: no session's stream, reviewer's words, gate finding, clause reason or node free text, and of what sessions name only node ids (held to the store's pattern at every write), units as the unit registry names them, and quantity names that are the gate catalogue's; anything else by its place |
| `completion.py` | The preconditions of completion (ARCH-051): an ordered registry of named entries, each asked with the run's state and a module and answering why it is open. The three here: every subtask planned in the module's directory merged; the system-scope result passed or the gate is off; and the latest contract result of every pair the module takes part in passed (none in a run without contract pairs). A later precondition is one more entry; replay asks the registry as it stands for every completion line, so an entry must hold on every run recorded before it |
| `escalation_state.py` | What a backend is shown about an attempt that ended without a merge: five parts, each copied from one record (the ledger line, the line that ended the attempt, the change check's proposed nodes, the gate line, the review line), with no free text. Built from the run as its event log replays, never from an open ledger or store |
| `replay.py` | `RunState`: the run's position, rebuilt from the event log, refusing a line that cannot come next at write time and at replay alike. After the integration call no line about a subtask may follow but a worktree removal, a person's decision, or a line of integration's own subtask where the call lets it run; that subtask is the one whose planning line marks it as the completion owner's, planned last in the integration module directory, read from that line and never from the register or a role's name, so a register changed since cannot change how a recorded run replays. A person's decision that acts on a design the call skipped as incomplete reopens it, and under `off` so does one while a subtask but integration's has not merged. The task ledger is projected from it, and the merge precondition reads that ledger back from disk (ARCH-001). Whether an attempt end goes to the queue is read from its escalation decision line, which is admitted only when due, by the run's backend at its version, about the state the log implies, under the routing rule, and for `rules` with the rules' own answer. A log from before the binding names none and replays as if `rules` had answered. In a run whose plan names its interfaces' consumers, nothing is dispatched before the run's contract pairs are on the record, they are recorded once and nothing is planned after them, and they must be the pairs the plan's recorded lines give. Merged is not complete: integration's attempt records what it declares complete straight after its accepted change check, once, naming modules of the plan (each by the first subtask planned in its directory) once each in plan order; once that attempt merged and its diff found nothing, the record owes one completion line per declared module whose preconditions all hold, in plan order, and replay refuses any other, a line about a module no merged declaration names, a second, and one over an open precondition. A pair is owed its first contract result once the subtasks its two sides name have both merged with a clean diff, and a retest, never marked first, after every later clean merge in either side's module directory; replay refuses a result where none is owed, for another pair than the first owed in recorded order, marked first wrongly, or at another run head or journal revision than the record's, and any dispatch, integration call, declaration or completion while one is owed. Its definition's digest is held to the form of one, never to the code's digest now |
| `apply.py` | Node proposals applied, never trusted: read from the attempt commit, only those the attempt changed, the role from the plan, held to the hook's rules in the hook's order with the hook's reasons (an owner change, a kind change, a cross node not written by the owner of the cross nodes or a domain node written by it, a new interface node, a node from the owner of completion), all of them pre-checked on a scratch copy of the graph so an attempt is applied whole or not at all. Also the canonical store the loop holds, whose journal is read without opening it, and the check after each step, which asks the role register who owns each cross-cutting duty |
| `merge.py` | A run's git layout, the recorded unforced removal of a done subtask's worktree, (its own branch, an integration worktree, one branch and worktree per subtask kept across attempts), the orchestrator's templated attempt commit, the write-scope check (ARCH-005) that runs before the gate, and the merge: `--no-ff` of exactly the checked commit, idempotent, a conflict aborted and raised |
| `git.py` | The git plumbing, with the user's and system's configuration off and repository hooks disabled |
| `ports.py` | The narrow Protocols the loop is handed for what it does not decide: the session, the change check, the merge, the graph diff |
| `events.py` | The run-event log. It is the loop's only memory: one synced, append-only line per stage transition and per decision. Each line carries its sequence number, UTC timestamp, run id and gate mode. A line the replay would refuse is refused before it is written; a run's planning line is also held, as it is written and only then, to the role register (an instrument's own log, which follows no run, is not): the subtask of the role that owns completion carries the completion mark, no other does, and with no single owner none is marked. The mark is a JSON `true`, or absent: a number, a `null` or a `false` in its place is a line this package could not have written. A completion declaration and a module's completion line are held, as they are written, to the register too: the declaring subtask is of the one role that owns completion, and with none or two nothing is written |
| `run_config.py` | Every input a run is reproduced from (the escalation binding among them, by register name; a configuration recorded before it reads as naming none, its digest unchanged), written once before the first action: seed, auth mode, model strings, bounds, gate mode, token ceiling, effort level and output-token limit (both passed to the binary, since left unset they come from a catalog the version does not pin), whether the run is reportable, the endpoint with any credential stripped, and the harness checkout it ran from (commit, clean or not, a digest of anything uncommitted). None has a default. A reportable run starts only from a clean commit; a run or resume under a different configuration, endpoint or harness is refused |
| `protocols.py` | The `Gate` and `Reviewer` Protocols the loop calls, in that order, and the result shapes they hand back: a gate result carries one record per check and the digest of the catalogue that judged it, and its verdict follows from the records. No implementation of either ships here. Also the refusal to run a reviewer on the implementer's model string (ARCH-060) |
| `accounting.py` | The token account, rebuilt from the event log: every token attributed to decomposition, a role session, a reviewer or routing, deduplicated by message id, and routing asserted zero. `total()` is the run's headline figure, every attribution summed with each message once |
| `budget.py` | The repair budget of three (ARCH-030), and the classifier that keeps infrastructure failures (API error, wall clock, turn limit, no result, unexpected exit) out of it. The binary's result is read by `is_error` and `terminal_reason`, never `subtype` |
| `repair.py` | Repair instructions as fixed templates filled from the finding: attempt 1 the finding, attempt 2 plus the failing check and its number with unit, attempt 3 none (it escalates) |
| `queue.py` | The approval queue: one append-only file, items carrying ARCH-130's five things, a person's decision as its own line. `ApprovalQueue` writes items (it creates its files and cuts a torn items tail on open). Every decision is written by `record_decision`, which the command, `ApprovalQueue.resolve` and the operator UI all call: under a lock on the decisions file, every file opened beneath the run directory without following a link and never created, the item open and (when a view is sent) still as shown. `read_queue` and `queue_listing` read through the same parser and write nothing; `physgate queue list` prints from them. A subtask the escalation decision sent to a person with attempts left has an item of its own (`decided_item`). Every read is capped (items 64 MiB, decisions 16 MiB, an event log or a stream 256 MiB) and every open non-blocking; the lock is waited on for at most 10 s, then the decision is refused |
| `decisions.py` | What a person's decision on a queue item does (ARCH-133), computed by code from the event log and never from the decision's words: one function says what each verb will do when an item is listed (`item_consequence`), what a decision does when the loop takes it at a boundary (`decision_effect`), and whether a replayed `decision_taken` line could have been written (`require_taken`). Approve merges only an attempt every automated check let through, of a subtask no review of which confirmed a reward-hacking indicator; reject orders the one fix after a blocked review, a retry while the budget lasts, or the end of the subtask. An integration failure and an arbitration record only (the arbitration's effect sits behind one function of its own). Under `queue_decisions: record` nothing here runs |
| `gate_events.py` | The catch-accounting events (ARCH-083): one per gate check, derived from the gate lines of the run-event log, and for a pass the number of things it evaluated. Each says whether the paired reviewer had passed the artefact, with the review line it came from and why that one: the same attempt's review (the one after the gate line in the loop's order, or the one before it in the injected-error instrument's blind order, never across a resume or a new session), or at integration the review of the attempt that last wrote the record's node. `gate_checks` gives the same events from the same derivation, each beside its record's bound, message and details (for an unchecked record, why nothing could judge it), for a reader that shows a check rather than counts it; `physgate gate-events` prints the events alone, unchanged |
| `change_sets.py` | What changed together in a run, from the log alone: the baseline decomposition recorded, and each merged attempt's revisions, handed to the integration call for the propagation check |
| `catches.py` | The catch count per gate mode and check over any runs and window: the headline is distinct artefacts caught after a reviewer had passed them, with the events and the checks run beside it |
| `common.py` | The small shapes the records share: the gate mode (defined by the flag register), the full-model-string rule |
| `exceptions.py` | The domain exceptions. All of them carry a context mapping |

## What it deliberately does not own

- **Any gate check or any reviewer.** The loop calls a gate and a reviewer
  through Protocols, and ships no implementation that passes work. The
  physics gate lives in `physgate.gate`; the command registers it.
- **The graph store and the task ledger.** Those are `physgate.state`'s. The
  ledger is written here, as a projection of the run-event log, because its
  line shape is fixed by the architecture and cannot hold a stage or a cause.
- **The hooks.** Sessions run under `physgate.hooks`; this package generates
  their settings and spawns them, and never edits what the hooks enforce.

## The run-event log and the task ledger

The ledger holds one line per change of a subtask's state, with the fields
ARCH-012 names. The event log holds everything else the loop needs to resume:
stages, causes, timestamps. Resuming reads the event log and nothing held in
memory.
